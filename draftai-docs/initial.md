# 🗺️ Project Development Roadmap

## 📌 Project Overview & Introduction
This application is a smart content assistant designed for developers and tech writers. It allows users to turn a single topic or prompt into a full-length technical article for DEV.to and a LinkedIn post at the same time. The tool automatically creates matching cover images, lets users review and edit drafts, and handles the publishing schedule. When it is time to post, it publishes to DEV.to first, grabs the link to the live article, injects that link into the LinkedIn post text, and then publishes to LinkedIn when credentials are configured. **If LinkedIn API credentials are not configured, v1 falls back to a ready-to-copy post (with the live DEV.to link injected) for manual posting.** Users have total control over their distribution setup and generation engine through a dedicated configuration dashboard. Here, they can easily toggle platforms on or off, securely save their custom API credentials, account details, and profile URLs, and fully configure their preferred AI agents (such as choosing specific LLM providers, local or cloud models, system instructions, and creativity settings).

## Phase 1: Requirements Documentation

### 📄 Business Requirements Document (BRD)
* **Objective**: Automate technical content distribution.
* **Core Value**: Saves developers hours weekly by transforming one core topic into multi-platform formats.
* **Success Metric**: Zero-friction scheduling, cross-platform tracking, and automatic dynamic link back-filling.
* **User Personas**: Technical writers, developer advocates, and independent software engineers.
* **Tenancy Model**: Full SaaS from day one — each registered user owns encrypted platform and AI credentials (BYOK).
* **v1 Account Model**: Single user per account (`USER` role only); team roles (`EDITOR`, `PUBLISHER`) reserved in schema for future releases.

### 📋 Software Requirements Specification (SRS)
* **Functional Scope**: Multi-field prompt engine, synchronous AI image generation, preview/refining editor, kanban/calendar history board.
* **Configuration Management**: Multi-tenant platform settings matrix — users toggle target platforms independently, store DEV.to API keys, profile URLs, and per-user encrypted AI provider keys (OpenAI, Anthropic, etc.).
* **AI Agent Extensibility**: Provider-agnostic AI factory; users bring their own API keys (BYOK), choose models (e.g., GPT-4o, Claude 3.5 Sonnet), tune temperature, and override system prompts.
* **Image Generation**: Cover images for all enabled platforms (DEV.to, LinkedIn, etc.) are auto-generated by AI from article title and content; images are persisted to object storage (not ephemeral provider URLs).
* **Scheduling Logic**: Staggered ARQ job queue — LinkedIn step fires only after extracting the live DEV.to slug and injecting it into the post text.
* **LinkedIn Fallback**: When LinkedIn API credentials are missing, system prepares copy-to-clipboard post text with live link.
* **DEV.to Auth**: API key only.
* **Performance Target**: AI assets must fully render within 120 seconds of prompt submission.
* **Security Guardrails**: Application-level encrypted credential storage (per-user); RBAC route protection; role enum includes `USER`, `EDITOR`, `PUBLISHER`, `ADMIN`, `SUPER`.

### 📦 Data Model (Content Entities)
Separate tables per asset (not a single nested JSON blob):
* `content_draft` — parent record, lifecycle state, prompt metadata
* `devto_article` — title, body (Markdown), tags, cover image ref
* `linkedin_post` — post text, cover image ref, injected article URL
* `cover_image` — storage key, provider metadata, platform association
* `platform_config` — per-user encrypted DEV.to API key, profile URLs, platform toggles
* `ai_agent_config` — per-user encrypted BYOK keys, model, temperature, system prompt
* `publish_job` — ARQ job state, retry count, platform outcomes

### 🏗️ Software Design Document (SDD)
* **System Pattern**: Layered modular framework mirroring the FastAPI template.
* **State Engine**: Strict lifecycle orchestration (`DRAFT` ➔ `APPROVED` ➔ `SCHEDULED` ➔ `PUBLISHED` | `PARTIALLY_PUBLISHED` | `FAILED`).
* **Settings Architecture**: Decoupled credential manager — per-user encrypted keys in PostgreSQL; platform secrets never in plain `.env` (only app master key and infra config in env).
* **AI Factory Layer**: Provider-agnostic LLM + image interface; initialises user's chosen model and BYOK credentials on a per-request basis.
* **Worker Layer**: **ARQ** (async Redis queue) — native asyncio, lightweight, pairs cleanly with FastAPI; separate worker process/container sharing backend code.
* **Storage Matrix**: **MinIO** in local Docker (S3-compatible, zero cost); **AWS S3** or **Azure Blob Storage** in production (most cost-effective object storage on each cloud).
* **Failure Model**: Tenacity for synchronous API calls; ARQ retry with exponential backoff for publish jobs.

### 📊 UML / C4 Structural Models
* **C4 Level 1 (Context)**: User interacts with web dashboard; system calls user-configured OpenAI/Anthropic, DEV.to API, and LinkedIn API; falls back to clipboard export for LinkedIn when credentials are absent.
* **C4 Level 2 (Container)**: **Vite/React** frontend → FastAPI backend → PostgreSQL + Redis; ARQ worker container; S3-compatible object storage.
* **C4 Level 3 (Component)**: ARQ worker listens on Redis to execute delayed multi-stage publish jobs (DEV.to first, then LinkedIn or clipboard-ready state).
* **Sequence Flow**: `Submit Prompt` ➔ `Check Enabled Platforms` ➔ `Fetch AI Agent Configs` ➔ `Gen Text + Cover Images via BYOK LLM` ➔ `Persist to Object Storage` ➔ `User Approval` ➔ `Queue ARQ Job` ➔ `Post DEV.to` ➔ `Inject Link` ➔ `Post LinkedIn OR Export to Clipboard`.

### ☁️ Cloud Deployment Notes (AWS / Azure)
* **Frontend**: S3 + CloudFront (AWS) or Static Web Apps / Blob + CDN (Azure) — static Vite build from `/frontend`.
* **Backend + Worker**: ECS Fargate, App Runner, or Container Apps — two services, same image, different entrypoints (`api` vs `arq worker`).
* **Data**: RDS PostgreSQL or Azure Database for PostgreSQL; ElastiCache Redis or Azure Cache for Redis.
* **Files**: S3 or Azure Blob — pay-per-GB, no compute cost for images.
* **CI/CD**: Path-filtered pipelines (`backend/**`, `frontend/**`) from monorepo.

### 🔌 Local publish setup (ngrok + LinkedIn env vars)
For local testing of publish flow:

1. Run `ngrok http 8000`
2. Set `PUBLIC_API_BASE_URL` in `backend/.env` to the ngrok HTTPS URL
3. Optional LinkedIn auto-post:
   - `LINKEDIN_ACCESS_TOKEN=<oauth-access-token>`
   - `LINKEDIN_AUTHOR_URN=urn:li:member:<numeric-member-id>` (or `urn:li:company:<numeric-company-id>`)

If LinkedIn env vars are missing, DraftAI keeps clipboard fallback mode for manual LinkedIn posting.
